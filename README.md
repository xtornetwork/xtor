# xray-onion — «луковая» сеть на туннелях Xray

Аналог Tor на VLESS + Reality. Трафик клиента идёт через три узла, каждый
следующий туннель вложен в предыдущий, и ни один узел не знает одновременно
клиента и цель.

```
клиент ══Reality+Vision══► guard ══Reality══► middle ══Reality══► exit ──► интернет
        │                  видит: клиента,   видит: guard,       видит: middle,
        │                  адрес middle      адрес exit          цель
        └── SOCKS5 127.0.0.1:9050 · HTTP 127.0.0.1:9080
```

Всё в одном бинарнике: директория, узел и клиент — это команды одной программы.
Ядро Xray подключено библиотекой, поэтому отдельный Xray ставить не нужно, а
цепочки и списки соседей меняются на ходу, без перезапуска и обрыва соединений.

## Сборка

```bash
go build -o xray-onion .
```

Единственная зависимость — `github.com/xtls/xray-core`. Reality и Vision
остаются оригинальной реализацией XTLS, ничего не переписано.

## Команды

| Команда | Что делает |
|---------|------------|
| `xray-onion install directory` | развернуть директорию: ключ, токены, служба systemd, запуск |
| `xray-onion install node` | развернуть узел: ключи, описание, служба systemd, запуск |
| `xray-onion directory` | запустить директорию |
| `xray-onion node` | запустить узел |
| `xray-onion client` | запустить клиент (SOCKS5 и HTTP-прокси) |
| `xray-onion keygen` | выпустить ключи Reality и UUID |
| `xray-onion mint <файл> <имя>` | выпустить индивидуальный токен регистрации |

## Развёртывание

### 1. Директория

```bash
sudo ./xray-onion install directory
```

Создаёт системного пользователя, каталоги, ключ Ed25519 и службу
`xray-onion-directory`, после чего печатает публичный ключ. Слушает
`127.0.0.1:8500`, наружу публикуется через nginx или Cloudflare; при работе за
прокси добавьте `-behind-proxy`.

Токены бывают трёх видов:

- **индивидуальный токен узла**, привязанный к имени: утечка с одного узла не
  позволяет регистрировать другие;
- **токен чтения консенсуса**, пустой означает открытую сеть, как в Tor;
- **токен выдачи мостов**, без него непубличные узлы не отдаются никому.

Выпуск токена узлу (метка нужна только вам, закрепление идёт по личности):

```bash
sudo -u xrayonion xray-onion mint /etc/xray-onion/tokens.json relay1
```

Директория не верит heartbeat на слово: фоновый обходчик открывает TCP-соединение
на адрес и порт каждого узла и публикует только те, что действительно слушают.
Ограничены общее число узлов, число узлов с одного адреса и уникальность пары
адрес-порт. Токен закрепляется за личностью узла при первом использовании, и
другой узел им уже не зарегистрируется.

### 2. Узлы

Нужно минимум два guard, один middle и один exit, лучше шесть-десять узлов
разных операторов.

```bash
sudo ./xray-onion install node
```

Спросит имя, сайт-прикрытие, роли, родню, адреса директорий и токены к ним,
выпустит ключи, напишет `/etc/xray-onion/node.json` и поднимет службу
`xray-onion-node`. Отдельный Xray не требуется. Директорий можно указать
несколько через запятую, по токену на каждую: узел обязан попасть в набор
каждой, иначе он не наберёт кворум у клиентов.

Роли: **guard** — входной хоп, клиент подключается к нему с `xtls-rprx-vision`,
что скрывает TLS-в-TLS от DPI на единственном наблюдаемом участке; **middle** —
промежуточный; **exit** — выход в интернет. Узел может совмещать роли.

Установка заводит узлу долговременную личность и печатает её имя. Сообщите это
имя операторам ваших других узлов, чтобы объявить родство.

Непубличный узел (мост) задаётся флагом `-private`: он не попадает в общий
консенсус и выдаётся только по токену. Смысл в том, что читатель публичного
списка видит все адреса сети и может заблокировать её целиком.

### 3. Клиент

```bash
./xray-onion client -directory https://dir.example.com -dir-key <ключ> -rotate 30m
```

Поднимает SOCKS5 на `127.0.0.1:9050` и HTTP-прокси на `9080`. Имена резолвятся
на выходе, поэтому в curl нужен `socks5h://`, а в браузере — «Proxy DNS».

| Флаг | Значение |
|------|----------|
| `-dir-key` | публичные ключи директорий через запятую, иначе доверие при первом обращении |
| `-quorum` | сколько директорий должны подтвердить узел, 0 это большинство |
| `-allow-no-log` | работать с директорией без журнала прозрачности |
| `-bridge-token` | забрать мосты и строить цепочки только через них |
| `-bridge-file` | список мостов из файла, если директория недоступна |
| `-circuits` | сколько цепочек держать, по умолчанию 4 |
| `-guards` | сколько входных узлов закрепить, по умолчанию 2 |
| `-rotate` | период полного круга ротации, слоты меняются по очереди |
| `-bw-cap` | во сколько раз вес узла может превышать медианный |
| `-fingerprint` | отпечаток TLS, по умолчанию `firefox` |
| `-asn-file` | таблица ip2asn-v4.tsv: разводить цепочку ещё и по автономным системам |
| `-verbose` | печатать каждое соединение с указанием цепочки |

## Почему директория не может встать посередине

Клиент аутентифицирует каждый хоп по ключу Reality, который узнаёт из
консенсуса. Пока дескриптор подписан только директорией, она может подменить
этот ключ на свой и законно оказаться посередине цепочки, а клиент ничего не
заметит. Одна подпись директории эту дыру не закрывает.

Поэтому у узла есть вторая, долговременная пара Ed25519 — его личность:

- **Имя выведено из ключа.** Имя личности это усечённый хеш её открытого ключа,
  и по имени всегда можно пересчитать, тот ли это ключ. Подсунуть чужую подпись
  под нужным именем нельзя.
- **Дескриптор подписывает сам узел.** Подпись покрывает адрес, порт, ключ
  Reality, shortId, SNI, роли, родню, скорость, политику портов и срок годности.
- **Директория ничего не переписывает.** Она хранит и отдаёт подписанное
  побайтово, а её собственная подпись означает лишь «вот набор, который я
  видела». Приведение полей к канону делает узел, до подписи.
- **Клиент проверяет всё сам.** Подпись, соответствие имени ключу, срок
  годности. Негодный дескриптор отбрасывается.

После этого подменить ключ Reality директория не может. У неё остаётся право
умолчать об узле или показать разным клиентам разные наборы, и это закрывает
кворум.

Адрес входит в подпись, поэтому узел узнаёт свой внешний адрес у директории
при первой регистрации и сразу переподписывает дескриптор. Директория
отвергает дескриптор, чей адрес не совпадает с тем, что она видит.

## Кворум директорий

Директории независимы и между собой не переговариваются: каждая сама проверяет
узлы и публикует то, что видит. Узел регистрируется во всех, клиент опрашивает
все и берёт узел, о котором сказали не меньше заданного числа директорий.

```bash
./xray-onion client   -directory https://d1.example,https://d2.example,https://d3.example   -dir-key <k1>,<k2>,<k3> -quorum 2
```

По умолчанию кворум это большинство. Для одной директории он равен единице, то
есть поведение не меняется.

- **Умолчать об узле** теперь может только сговор кворума директорий: если одна
  скрыла узел, остальные его назовут.
- **Подсунуть свой узел** в одиночку нельзя: узел без кворума в цепочки не
  пойдёт, и клиент пишет об этом в лог. Так же выглядит и отставшая директория,
  поэтому запись стоит читать.
- **Недоступность части директорий** не ломает работу, пока отвечает кворум.
  Если отвечает меньше, клиент отказывается строить цепочки, а не берёт то, что
  дали.
- **Разные версии дескриптора** у разных директорий это норма: узел
  переподписывает его по сроку. Побеждает самый свежий, а голоса считаются по
  личности узла.
- **Мосты** раздаются адресно и по определению известны не всем директориям,
  поэтому к ним кворум не применяется, берётся объединение. Подпись узла
  проверяется всё равно.
- **Журнал прозрачности** проверяется у каждой директории отдельно, см. ниже.

Список соседей промежуточные узлы тоже берут через кворум: иначе одна
директория вписала бы свой адрес и заставила узел ходить к ней.

## Журнал прозрачности

Кворум мешает директории умолчать об узле, но не доказывает, что она показала
всем одно и то же. Директория может вести две истории: одну для большинства,
другую для выбранного клиента. Снаружи это неотличимо.

Журнал делает раздвоение обнаружимым. Каждый набор узлов, который директория
когда-либо отдавала, становится листом дерева Меркла, как в Certificate
Transparency. Директория подписывает корень и размер дерева и по запросу
доказывает две вещи:

- **включение**: набор, который вы получили, действительно лежит в дереве;
- **согласованность**: дерево с прошлого раза только дополнялось, ничего в нём
  не переписывали.

Клиент помнит последний подписанный корень каждой директории и требует
согласованности при каждом обращении. Переписанная или усечённая история
всплывает сразу, и данные такой директории не считаются.

**Свидетельствование.** Одной памяти клиента мало: директория может вести
ровную историю лично для него. Поэтому директории следят за корнями друг друга
и отдают увиденное:

```bash
xray-onion directory ... -witness https://d2.example,https://d3.example
```

Клиент забирает эти свидетельства и требует связать чужой корень со своим одним
доказательством согласованности. Две несводимые истории связать нельзя, и
директория попадается.

Журнал обязателен по умолчанию. Директория без него не принимается, пока
клиенту явно не сказано `-allow-no-log`. Исчезновение журнала у директории,
которая его вела, считается подлогом.

## Как противник не занимает две позиции сразу

Криптография не помогает против противника, который держит и вход, и выход
одной цепочки: он сопоставит трафик по таймингу. Помогает только развязка.

- **Родство засчитывается только взаимное.** Узел перечисляет имена личностей
  своих собратьев, и клиент разводит два узла по разным цепочкам, лишь когда
  оба назвали друг друга. Одностороннего заявления мало: иначе враждебный узел
  объявил бы роднёй пол-сети и вытеснил честные узлы из цепочек со своим
  участием.
- **Разные сети.** В одной цепочке не встречаются узлы из одной /16.
- **Разные автономные системы.** Разные /16 бывают у одного провайдера. Дайте
  клиенту таблицу `ip2asn-v4.tsv` флагом `-asn-file`, и цепочка разведётся ещё
  и по номерам AS. Узлы вне таблицы не отбрасываются.
- **Закрепление входных узлов** и **ограничение веса** по скорости, описанные
  ниже, ограничивают перебор позиций.

## Как это устроено

**Слоты вместо перезаписи правил.** Маршрутизация клиента задаётся один раз:
`slot-N` ведёт в `exit-sN`. Смена цепочки — это снятие и добавление трёх
outbound за теми же тегами. Снятие обработчика не закрывает уже открытые
потоки, поэтому ротация не рвёт соединения; слоты обновляются по очереди.

**Политика соседей без перезапуска.** Guard и middle обязаны выпускать трафик
только на другие узлы сети, иначе это открытый прокси. Список соседей меняется
постоянно, и в правилах маршрутизации это означало бы перезапуск ядра при
каждом изменении. Поэтому политика вынесена в подменённый системный дозвонщик:
список обновляется атомарно. Фолбэк Reality на сайт-прикрытие ходит мимо этого
дозвонщика, своим дозвоном, поэтому маскировка продолжает работать.

**Защита выходного узла.** Маршрутизация выхода резолвит имена до сопоставления
правил. Без этого блокировка приватных сетей обходилась бы именем, которое
резолвится в приватный адрес, и каждый выход становился бы входом в локальную
сеть своего оператора. Политика портов задаётся в описании узла и публикуется в
дескрипторе, поэтому клиент знает, какая цепочка какой порт не пропустит.

**Выбор пути.** Случайность берётся из криптостойкого источника: состояние
обычного генератора восстановимо по наблюдаемой выдаче. Входные узлы
закрепляются по имени личности и переживают временную недоступность, иначе
противник, умеющий ронять узлы, перебирал бы клиента на свой guard. Вес по
пропускной способности ограничен медианой, умноженной на коэффициент, потому
что скорость узел сообщает о себе сам.

**Изоляция по назначению.** Один хост всегда идёт через одну цепочку, как
`IsolateDestAddr` в Tor. Привязка устойчива к падению цепочек, поэтому потеря
одной не перемешивает остальные.

**Живость цепочек.** Ядро отдаёт соединение до завершения рукопожатия, поэтому
ответ SOCKS оптимистичен и успешный дозвон ничего не доказывает. Цепочка
считается живой, если по ней пришли данные, и мёртвой, если запрос ушёл, а
ответа не было. Если клиент сам ничего не отправил, счётчики не трогаются.

**Кеш последнего набора.** Клиент запоминает набор узлов, прошедший кворум и
проверку журналов. Если директории недоступны, он поднимается на этом наборе
вместо того, чтобы останавливаться целиком: узлы-то живы. Кеш безопасен ровно
потому, что дескрипторы подписаны самими узлами и несут срок годности, поэтому
подменить его нельзя, а через сутки он пустеет сам. Просроченные узлы
отбрасываются по одному, и работа продолжается на живой части. Возраст кеша не
обновляется от самого факта его использования, иначе он выглядел бы свежим
вечно. Вернувшиеся директории всегда важнее кеша.

**Время жизни контекста.** Из того же свойства следует неочевидное: дозвон
продолжается в фоне и привязан к контексту, с которым его позвали. Если
отменить контекст сразу после возврата соединения, оборвётся ещё не
законченное рукопожатие дальних хопов, и цепочка длиннее двух узлов работать не
будет. Поэтому контекст живёт ровно столько, сколько соединение, и отменяется
при его закрытии, а не по тайм-ауту.

## Сайт-прикрытие

Reality проксирует рукопожатие на сайт-прикрытие, поэтому он обязан быть
доступен с узла и подходить по параметрам TLS. Проверено на этой версии Reality:
`www.cloudflare.com`, `dl.google.com` и `www.apple.com` работают,
`www.microsoft.com` не работает — рукопожатие не завершается. Для обхода
блокировок выбирайте сайт, доступный из целевой страны, и проверяйте оттуда.

## Тесты

```bash
go test ./...
```

Среди прочего поднимаются три настоящих узла и клиент, после чего HTTP-запрос
проходит через настоящий SOCKS5 клиента и всю цепочку с вложенными
рукопожатиями Reality. Отдельные тесты доказывают, что ротация цепочки не рвёт
открытое соединение и что контекст дозвона живёт, пока живо соединение.
Быстрый прогон без сети: `go test -short ./...`.

Проверено и вживую, тремя отдельными процессами: запрос проходит через SOCKS5 и
через HTTP-прокси, а по логам узлов видно главное свойство сети — guard видит
только адрес middle, middle только адрес выхода, выход только цель:

```
guard1:  accepted tcp:127.0.0.1:18544      (адрес middle)
middle1: accepted tcp:127.0.0.1:18545      (адрес выхода)
exit1:   accepted tcp:api.ipify.org:443    (цель, но не клиент)
```

Детектор гонок требует cgo и gcc; на машине сборки их не было, поэтому
`go test -race` не запускался.

## Стенд

```bash
docker compose -f lab/docker-compose.yml up -d --build
curl --socks5-hostname 127.0.0.1:9050 https://api.ipify.org
docker compose -f lab/docker-compose.yml down -v
```

Директория, два моста, четыре публичных узла и клиент — всё из одного образа.

## Чем отличается от Tor

| Свойство | Tor | xray-onion |
|----------|-----|------------|
| Послойное шифрование | свой протокол | три вложенных TLS 1.3 Reality |
| Сопротивление DPI | нужны bridges и obfs4 | Reality и Vision из коробки |
| Непубличные входные узлы | bridges | выдача по токену |
| Директория | девять авторитетов, голосование | независимые директории, кворум на стороне клиента |
| Обнаружение подлога директории | нет | журнал Меркла, включение и согласованность |
| Дескриптор узла | подписан самим узлом | подписан самим узлом |
| Имя узла | отпечаток ключа | имя выведено из ключа личности |
| Родство операторов | засчитывается взаимное | засчитывается взаимное |
| Вес узлов | измеряют отдельные авторитеты | узел измеряет себя сам, вес ограничен |
| Изоляция потоков | встроенная | по хосту назначения |
| Размер анонимного множества | миллионы пользователей | ваши узлы и ваши пользователи |
| Постоянный размер ячеек | 514 байт | нет |
| Тайминг-корреляция | уязвим | уязвим так же |
| Onion-сервисы | есть | нет |
| UDP | нет | нет: изоляция определена для TCP |

Директория знает все узлы, но не видит цепочек: их выбирает клиент. Оператор,
контролирующий guard и exit одной цепочки, сопоставит трафик по таймингу, как и
в Tor; защита та же — узлы разных операторов и сетей.

## Что осталось за рамками

- UDP: SOCKS5 ASSOCIATE отклоняется, изоляция по назначению определена для TCP.
- Ограничение числа соединений с одного адреса: ядро не отдаёт точку врезки в
  приём, поэтому лимит нужно ставить снаружи, например через nftables.
- Отдельный предел возраста кеша: сейчас он ограничен только сроком годности
  дескрипторов, то есть сутками.
- Разнос свидетельств не только между директориями, но и через узлы и клиентов:
  сейчас корни расходятся только по кругу директорий, и сговор всего круга
  остался бы незамеченным.
- Хранение журнала в сжатом виде: сейчас он растёт на один лист при каждом
  изменении состава сети и никогда не усекается.
- Независимое измерение скорости узлов вместо самооценки.

Прежняя реализация на Python лежит в `legacy-python/` и больше не нужна.
